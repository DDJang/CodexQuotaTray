# CodexQuotaTray 产品需求文档（PRD）

**产品名称：** CodexQuotaTray
**产品形态：** Windows 系统托盘轻量应用
**文档版本：** V1.0
**目标平台：** Windows 10/11
**核心定位：** 随时查看 Codex 5 小时额度、7 天额度、重置时间及可用重置次数

---

## 1. 产品背景

Codex 用户在持续编程过程中，通常需要关注以下问题：

1. 当前 5 小时额度还剩多少？
2. 周期较长的周额度还剩多少？
3. 两个额度分别何时恢复？
4. 当前有多少次可用的额度重置？
5. 是否需要减少高消耗任务，或切换到更节省额度的模型？

目前官方提供 Codex Usage 页面，CLI 中也有 `/status` 和 `/usage` 等入口，但用户需要主动打开页面或执行命令，无法在编程过程中快速扫一眼获取状态。官方说明显示，本地消息与云任务共享同一个 5 小时额度窗口，并且还可能存在额外的周限制。

CodexQuotaTray 的目标不是重新计算额度，而是以低性能开销读取官方返回的账户额度数据，并在系统托盘中进行简洁展示。

---

## 2. 产品目标

### 2.1 核心目标

让用户在不离开当前编程环境的情况下，在 1 秒内回答三个问题：

* 5 小时额度还剩多少？
* 周额度还剩多少？
* 还有几次可用重置？

### 2.2 体验目标

* 信息一眼可读，不要求打开完整应用窗口。
* 默认不遮挡 Codex、VS Code、终端或浏览器。
* 后台运行时几乎无感。
* 不频繁请求网络。
* 不读取浏览器 Cookie，不抓取网页 DOM。
* 不默认使用或消耗重置次数。
* 数据异常时明确告诉用户数据是否过期。

### 2.3 非目标

MVP 阶段不包含：

* 预测“还能发送多少条消息”。
* 精确预测某个任务将消耗多少额度。
* 绕过或修改 Codex 官方额度限制。
* 自动购买 Credits。
* 自动使用额度重置。
* 分析具体代码内容或 Codex 对话内容。
* 自建服务器同步用户账户数据。

Codex 的实际消耗受到模型、上下文、推理、工具调用、缓存和任务复杂度等因素影响，因此不应把剩余额度转换成固定的“剩余消息条数”。

## 3. 展示位置方案

### 3.1 推荐方案：系统托盘

CodexQuotaTray 常驻 Windows 右下角系统托盘。

这是首选方案，原因如下：

* Codex 桌面端、CLI、IDE 和网页端均可使用。
* 不占用任务栏主区域。
* 不遮挡编辑器和终端。
* 无需持续绘制悬浮窗口。
* 用户已形成“托盘查看后台状态”的使用习惯。
* 可以通过悬停、单击和右键提供不同层级的信息。

### 3.2 信息展示层级

#### 第一层：托盘图标

托盘图标只表达总体状态，不尝试在 16×16 图标中展示具体百分比。

图标状态：

* 正常：两个额度均充足。
* 注意：任一额度剩余不高于 20%。
* 紧张：任一额度剩余不高于 5%。
* 耗尽：某个额度已达到限制。
* 灰色：未登录、网络异常或数据不可用。
* 刷新标记：正在更新数据。

不能只依赖颜色，应同时改变图标角标或轮廓，例如：

* 正常：完整圆环。
* 注意：圆环带感叹号。
* 耗尽：圆环带叉号。
* 离线：圆环带短横线。

#### 第二层：鼠标悬停提示

鼠标悬停时显示一行摘要：

```text
Codex：5小时 72% · 7天 41% · 重置 2次
```

额度较低时：

```text
Codex：5小时 8% · 7天 35% · 重置 1次
```

数据不可用时：

```text
Codex：暂时无法获取额度 · 12:35最后更新
```

#### 第三层：单击展开卡片

单击托盘图标，弹出宽约 320–360 px 的轻量卡片：

```text
Codex 用量                         刚刚更新

5 小时额度
72% 剩余
██████████████░░░░░
14:30 重置 · 还有 2小时18分钟

7 天额度
41% 剩余
████████░░░░░░░░░░░
7月20日 06:20 重置

可用重置                         2 次
最早一项于 7月24日到期

[刷新]             [打开官方用量页面]
```

界面中必须同时显示：

* 剩余百分比。
* 进度条。
* 具体重置时间。
* 距离重置的倒计时。
* 可用重置次数。
* 最后更新时间。

### 3.3 不推荐作为默认方案的位置

#### 桌面悬浮窗

优点是始终可见，但会：

* 遮挡编辑器。
* 增加窗口管理复杂度。
* 持续吸引注意力。
* 产生额外的绘制和置顶处理。

可以作为后续可选功能，但不得默认开启。

#### VS Code 状态栏

适合只使用 VS Code 的用户，但不适用于：

* Codex 桌面端。
* Codex CLI。
* JetBrains IDE。
* 浏览器端 Codex。
* 同时打开多个编辑器的场景。

因此更适合作为 P2 扩展，而不是主产品入口。

#### Codex 窗口内部插件

信息位置最贴近 Codex，但依赖 Codex UI 和扩展能力，兼容风险较高，也无法覆盖终端和其他编辑器。

## 4. 用户画像

### 4.1 主要用户

频繁使用 Codex 进行以下工作的个人开发者：

* 在 VS Code 或其他 IDE 中调用 Codex。
* 使用 Codex CLI。
* 同时运行多个 Codex 任务。
* 使用较复杂代码仓库或长上下文。
* 经常接近 5 小时或周额度限制。
* 拥有可用的 banked rate-limit reset。

### 4.2 典型场景

#### 场景一：开始大型任务前

用户准备让 Codex 执行大范围重构，先查看周额度是否充足，再决定是否立即执行。

#### 场景二：连续使用过程中

用户正在 VS Code 中编程，不想切换到 Usage 页面，只需悬停托盘图标查看剩余额度。

#### 场景三：额度接近耗尽

5 小时额度降至 10%，应用进行一次低干扰提醒，用户决定缩小任务范围或等待恢复。

#### 场景四：存在重置次数

额度耗尽后，用户看到“可用重置 2 次”，再进入官方界面或组件的明确确认流程使用重置。

#### 场景五：数据异常

网络断开或官方接口暂时不可用，组件继续展示上一次数据，但标明“数据可能已过期”。

## 5. 核心功能需求

## 5.1 额度读取

系统需要读取：

* 当前账户及套餐类型。
* 所有可用额度窗口。
* 每个窗口的已使用百分比。
* 窗口时长。
* 下一次重置时间。
* 当前是否已经达到限制。
* 可用额度重置次数。
* 重置项的到期时间，如果官方返回该信息。

官方 Codex App Server 已提供 `account/rateLimits/read`，能够返回 `usedPercent`、`windowDurationMins`、`resetsAt`、限制状态以及 `rateLimitResetCredits.availableCount` 等数据。

### 5.1.1 剩余百分比计算

```text
remainingPercent = max(0, min(100, 100 - usedPercent))
```

展示时四舍五入为整数。

### 5.1.2 窗口识别

不得只根据 `primary` 和 `secondary` 字段硬编码含义，应优先根据 `windowDurationMins` 判断：

* 约 300 分钟：显示为“5 小时”。
* 约 10080 分钟：显示为“7 天”或“周”。
* 其他时长：显示为动态名称，例如“24 小时额度”。

这样即使官方以后调整周期，组件仍可正常展示。

若服务端提供 `limitName`，优先使用官方名称；没有名称时再根据时长生成。

### 5.1.3 重置次数

界面展示：

```text
可用重置：2 次
```

应以 `availableCount` 为最终依据，因为官方说明重置明细可能只返回部分项目，而总数量字段才是权威数据。

若存在明细，则额外显示：

* 最早到期时间。
* 每项状态。
* 重置类型。

---

## 5.2 自动刷新

### 5.2.1 刷新触发条件

按以下优先级更新数据：

1. 应用启动后立即读取一次。
2. 收到 `account/rateLimits/updated` 通知时更新。
3. 用户单击“刷新”时立即读取。
4. 从睡眠或休眠恢复后读取一次。
5. 网络从断开恢复后读取一次。
6. 无通知时，每 10 分钟进行一次兜底刷新。
7. 卡片打开且数据超过 60 秒未更新时，自动刷新一次。

官方 App Server 可在额度发生变化时发送 `account/rateLimits/updated` 通知，因此无需每几秒轮询。

### 5.2.2 防止过度刷新

* 两次主动请求间隔不得小于 10 秒。
* 连续失败时采用指数退避。
* 应用位于后台时不进行动画刷新。
* 仅更新倒计时文本，不需要每秒重新请求额度。
* 倒计时显示到分钟即可，剩余不足 1 分钟时才显示秒。

---

## 5.3 通知提醒

### 5.3.1 默认提醒阈值

每个额度周期分别支持：

* 剩余 20%。
* 剩余 5%。
* 已耗尽。
* 已完成自动重置。
* 新增可用重置次数。
* 某个重置将在 3 天内到期。

### 5.3.2 防打扰规则

* 同一额度窗口、同一阈值只提醒一次。
* 额度恢复或进入新窗口后重新激活提醒。
* 默认不播放声音。
* Windows 专注模式开启时尊重系统设置。
* 用户可以关闭所有通知，仅保留托盘显示。
* 不使用每下降 1%就提醒的方式。

### 5.3.3 通知文案

```text
Codex 5小时额度剩余 20%
预计于 14:30 重置。
```

```text
Codex 周额度剩余 5%
建议暂缓大型任务或使用更轻量的模型。
```

```text
Codex 额度已恢复
新的 5 小时使用窗口已经开始。
```

## 5.4 重置次数操作

### MVP

只展示重置次数，不允许在组件内直接使用。

理由：

* 使用重置属于不可轻易撤销的账户操作。
* 用户可能误点托盘。
* MVP 应优先保证只读、安全和稳定。

### P1

增加“使用一次重置”功能，但必须满足：

1. 用户主动展开重置区域。
2. 显示本次操作将重置的额度窗口。
3. 二次确认。
4. 使用唯一的 `idempotencyKey`。
5. 操作完成后重新调用 `account/rateLimits/read`。
6. 不根据本地数据自行推断重置结果。

官方 App Server 提供 `account/rateLimitResetCredit/consume`，并要求使用非空且可重试复用的幂等键；操作后应重新获取额度。

确认文案：

```text
使用一次 Codex 额度重置？

当前可用：2 次
重置可能存在有效期，使用后无法撤销。

[取消] [确认使用]
```

## 6. 信息架构

### 6.1 卡片主界面

从上至下依次为：

1. 产品名称和刷新状态。
2. 5 小时额度。
3. 7 天或周额度。
4. 可用重置次数。
5. 数据说明或异常提示。
6. 操作栏。

### 6.2 设置页

设置页只保留必要选项：

**常规**

* 开机启动。
* 启动时最小化到托盘。
* 单击托盘图标的行为。
* 显示剩余百分比或已用百分比。
* 时间格式：24 小时制或 12 小时制。

**通知**

* 20%提醒。
* 5%提醒。
* 耗尽提醒。
* 恢复提醒。
* 重置即将过期提醒。

**刷新**

* 兜底刷新间隔。
* 网络恢复时自动刷新。
* 手动刷新快捷键。

**隐私**

* 查看本地缓存位置。
* 清除本地缓存。
* 启用诊断日志。
* 打开隐私说明。

## 7. 状态设计

### 7.1 正常状态

显示最新额度、重置时间和重置次数。

### 7.2 正在刷新

保留已有数据，仅在更新时间旁显示轻量旋转标记。

不得清空界面或让进度条闪烁。

### 7.3 数据过期

当数据超过 15 分钟未成功更新：

```text
数据可能已过期 · 12:35最后更新
```

仍然展示上一次数据，但进度条降低视觉强调。

### 7.4 未登录

```text
尚未登录 Codex

登录后可查看账户的用量和重置次数。

[登录]
```

### 7.5 API Key 模式

若用户仅使用 API Key，ChatGPT 套餐的 5 小时和周额度可能不适用，应显示：

```text
当前使用 API Key 计费
此账户没有可显示的 ChatGPT Codex 套餐额度。
```

官方账户用量接口要求 Codex 服务账户认证，不适用于仅 API Key 或 Bedrock 的认证方式。

### 7.6 网络错误

```text
暂时无法连接到 Codex 服务
正在显示上一次成功获取的数据。
```

提供“重试”，但不弹出阻塞式错误窗口。

### 7.7 服务端缺少某个窗口

例如只返回 5 小时额度：

* 正常显示 5 小时额度。
* 周额度区域显示“当前账户未返回周额度”。
* 不显示为 100%。
* 不自行猜测周额度。

### 7.8 达到限制

若服务端明确返回 `rateLimitReachedType`：

```text
5 小时额度已用完
14:30 自动恢复
```

有可用重置时：

```text
可用重置：2 次
```

没有可用重置时不显示操作入口。

## 9. 技术方案建议

### 9.1 推荐架构

采用 Windows 原生轻量托盘程序：

```text
Tray UI
   │
Quota State Store
   │
App Server Client
   │ JSON-RPC / stdio
codex app-server
   │
Codex 官方服务
```

### 9.2 推荐技术栈

首选：

* Rust。
* `windows-rs` 调用 Windows 原生 API。
* 原生系统托盘。
* 原生或轻量自绘弹出卡片。
* JSON-RPC 与 `codex app-server` 通信。
* 本地 JSON 或 SQLite 保存非敏感设置。

不建议：

* Electron。
* 在后台启动完整 Chromium。
* 高频网页抓取。
* Playwright 常驻浏览器。
* 读取 ChatGPT 浏览器 Cookie。
* 直接调用未公开的网页内部接口。

### 9.3 App Server 生命周期

建议应用启动后：

1. 检查 Codex CLI/App Server 是否可用。
2. 启动一个长期存在的 `codex app-server` 子进程。
3. 完成 JSON-RPC 初始化。
4. 调用 `account/read` 检查账户状态。
5. 调用 `account/rateLimits/read` 获取额度。
6. 监听 `account/rateLimits/updated`。
7. 应用退出时优雅终止子进程。

避免每次刷新都重新启动 App Server，因为频繁创建进程会增加延迟和资源消耗。

### 9.4 数据源优先级

1. 官方 App Server `account/rateLimits/read`。
2. 官方额度更新通知。
3. 官方 Usage 页面作为用户手动核对入口。
4. 不使用本地历史日志推算官方剩余额度。
5. 不通过任务 Token 数量自行换算百分比。

Codex 官方也提供 Usage Dashboard，CLI 会话内可使用 `/status` 查看剩余额度，并可通过 `/usage` 查看账户用量或使用可用重置。

## 10. 性能要求

以下指标作为产品验收目标，而非对所有设备的绝对保证。

### 10.1 空闲资源

* 空闲平均 CPU：低于 0.1%。
* 空闲工作集内存：不高于 35 MB。
* 后台无持续动画。
* 后台无每秒定时器。
* 不常驻浏览器内核。
* 不扫描用户代码目录。

### 10.2 刷新资源

* 单次刷新完成后立即释放临时对象。
* 正常网络环境下，卡片打开后 1 秒内显示缓存数据。
* 官方数据刷新目标在 3 秒内完成。
* 刷新期间界面保持可操作。
* 同一时间只能存在一个额度请求。

### 10.3 安装体积

* 主程序及必要资源目标小于 20 MB。
* 不内置大型运行时。
* 不打包 Chromium。

### 10.4 启动性能

* 冷启动至托盘图标出现：目标小于 1 秒。
* 不阻塞 Windows 登录。
* App Server 初始化可以在托盘图标出现后异步完成。

## 11. 隐私与安全

### 11.1 数据原则

* 所有额度处理在本机完成。
* 不建设第三方后端。
* 不上传账户额度历史。
* 不读取代码仓库内容。
* 不保存 Codex 对话。
* 不保存访问令牌明文。
* 优先复用 Codex 官方登录和凭据管理机制。

### 11.2 本地缓存内容

允许缓存：

* 最后一次额度百分比。
* 重置时间。
* 可用重置次数。
* 最后更新时间。
* 用户设置。
* 已发送的通知阈值。

禁止缓存：

* OAuth Access Token。
* Refresh Token。
* 完整账户凭据。
* 用户对话正文。
* 项目代码。
* App Server 原始敏感响应日志。

### 11.3 日志脱敏

诊断日志不得包含：

* 用户邮箱。
* 账户 ID。
* Token。
* Cookie。
* Reset Credit 的完整内部 ID。
* 完整官方响应正文。

日志示例：

```text
2026-07-15 12:31:05 rate_limits_read success
primary_window=300m remaining=72
secondary_window=10080m remaining=41
reset_count=2
```

## 12. 特殊产品约束

### 12.1 共享额度提示

部分 Codex 用量可能与其他 agentic 功能共享，因此额度变化不一定全部由当前 Codex 窗口产生。组件只负责展示账户官方返回的额度状态，不对具体消耗来源进行归因。官方目前说明 ChatGPT Work 与 Codex 共享使用额度，部分其他 agentic 功能也可能使用同一额度池。

可在帮助提示中显示：

```text
此处显示账户级 Codex/Agent 用量。部分其他功能可能与 Codex 共用额度。
```

### 12.2 动态规则

官方额度、套餐及重置活动可能发生变化，因此：

* 不在代码中固定套餐总量。
* 不假设所有用户都有周额度。
* 不假设所有用户都有重置次数。
* 不假设重置永久有效。
* 不假设 `primary` 永远是 5 小时。
* 不根据套餐名称自行估算额度。
* 所有可展示数据以服务端返回为准。

Banked reset 的资格、数量、有效期和活动规则可能因套餐、工作区、地区或活动而不同。

## 15. 成功指标

### 使用指标

* 日活用户中，超过 60%每天至少查看一次托盘信息。
* 超过 80%的查看操作只通过悬停或托盘卡片完成。
* 打开完整 Usage 页面的次数明显低于托盘查看次数。
* 用户能在不打开设置页的情况下理解全部核心信息。

### 质量指标

* 额度展示与官方数据一致率不低于 99%。
* 崩溃率低于 0.1%。
* 空闲 CPU 达到性能目标。
* 连续运行 7 天无明显内存增长。
* 网络中断不会造成程序崩溃。
* App Server 异常退出后能够自动恢复一次。
* 不发生未经用户确认的重置消耗。

## 16. 验收标准

### AC-01：正常展示

给定服务端返回 5 小时额度已使用 28%，组件必须显示：

```text
5 小时额度：72%剩余
```

### AC-02：周额度展示

给定窗口时长约为 10080 分钟，组件必须识别为“7 天额度”或“周额度”。

### AC-03：重置时间

给定 `resetsAt`，组件必须按照 Windows 当前时区显示具体时间及倒计时。

### AC-04：重置次数

给定 `availableCount = 2`，即使仅返回一条重置明细，也必须显示“可用重置 2 次”。

### AC-05：数据过期

连续 15 分钟无法刷新时，必须保留最后数据并标记“数据可能已过期”。

### AC-06：低额度提醒

某窗口首次由 21%下降至 20%时发送一次通知；继续下降至 19%时不得重复发送20%通知。

### AC-07：窗口恢复

额度窗口重置后，进度显示更新，并重新允许下一周期的阈值提醒。

### AC-08：未登录

未登录时不得显示虚假的 100%额度，必须显示登录引导。

### AC-09：只读安全

MVP 中任何托盘单击、双击或右键操作均不得消耗额度重置。

### AC-10：性能

应用空闲 30 分钟后不得持续产生明显 CPU 占用或高频网络请求。

## 17. 最终产品形态

CodexQuotaTray 的默认体验应保持为：

* 平时只存在一个系统托盘图标。
* 悬停可看三项核心数据。
* 单击可看详细额度和重置时间。
* 额度紧张时只提醒一次。
* 数据更新以事件通知为主，低频轮询为辅。
* 不使用 Electron。
* 不抓网页。
* 不读取浏览器 Cookie。
* 不默认执行任何账户写操作。

最终用户感知应是：

> 它一直在那里，但几乎感觉不到它在运行；需要时看一眼，就能知道 Codex 还能用多少。
